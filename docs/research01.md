# Compressing the Indexer Key Matrix in Sparse Attention: Algorithms, Systems, and a Roadmap for DSA-Style Architectures

## TL;DR
- **The problem is real and named in the literature**: in DeepSeek Sparse Attention (DSA), the indexer key cache is ~132 bytes/token/layer (a 128-dim FP8 MQA key + 4-byte FP32 scale), and because it must be read for ALL history tokens every step, its cumulative read volume overtakes the fetched top-k latent KV at roughly 10K tokens of context — making it the growing bottleneck exactly as the query describes. No published system yet solves the specific "offload the Indexer K to remote memory and fetch it under bandwidth pressure" problem end-to-end, but every building block exists.
- **The highest-leverage techniques are (1) asymmetric quantization for inner-product search (ScaNN/anisotropic VQ, QJL, product quantization) applied to the indexer key, (2) hierarchical two-stage selection (HISA, NSA, RetroInfer's wave index) to cut how many keys must be fetched/scored, and (3) DeepSeek-V4's own move to an FP4 indexer cache**, which is the single most direct precedent for compressing Indexer K storage.
- **Recommended path**: keep the query at full precision and heavily compress the stored indexer key (asymmetric distance computation), add a block/centroid coarse filter so you only fetch full-precision keys for a small candidate set, and exploit cross-layer index reuse (IndexCache) to amortize fetches. Validate with recall@k of the top-2048 set rather than score MSE.

## Key Findings

### 1. The Indexer K footprint quantified
DSA's "lightning indexer" scores every historical token with a lightweight function `I_{t,s} = Σ_j w^I_{t,j} · ReLU(q^I_{t,j} · k^I_s)` over `H^I = 64` MQA heads with key dimension `d_I = 128`, then selects top-k = 2048 tokens for Sparse MLA. The indexer stores **keys only, not values**. In the SGLang implementation the buffer is 128 bytes (128-dim FP8/float8_e4m3 single MQA key) + 4 bytes (one FP32 per-block scale) = **~132 bytes per token per layer**, versus **656 bytes/token/layer** for the MLA latent KV (512 B FP8 NoPE latent + 16 B FP32 scales + 128 B bf16 RoPE) — roughly a 5× ratio.

The critical asymmetry: the indexer reads **all N tokens** each step, while the full 656 B latent is fetched only for the **fixed** top-k = 2048 tokens. Setting `N × 132 ≈ 2048 × 656` gives a crossover around **N ≈ 10,000 tokens**, beyond which the cumulative indexer-K traffic exceeds the latent KV actually fetched — precisely the regime the query targets. DSA reduces HBM *reads per step*, not KV *storage*: all N tokens' latent KV plus all N indexer keys still reside in memory.

### 2. Asymmetric quantization for inner-product search (the strongest match)
This is the most directly applicable family, because indexer scoring is exactly a Maximum Inner Product Search (MIPS) problem where only ranking matters, not score fidelity.
- **ScaNN / Anisotropic Vector Quantization** (Guo et al., ICML 2020): the key insight is that for MIPS the *parallel* component of quantization error (along the datapoint direction) disproportionately harms high inner products — the ones top-k cares about. Anisotropic loss penalizes parallel error more heavily, giving state-of-the-art recall at aggressive compression. This maps perfectly onto compressing the stored indexer key while keeping the query full precision (asymmetric distance computation). ScaNN combines product quantization + score-aware anisotropic loss + SIMD in-register 4-bit lookup tables.
- **QJL (1-bit Quantized JL Transform)** (Zandieh et al.): a Johnson–Lindenstrauss random projection followed by sign-bit (1-bit) quantization of keys, with a provably `1±ε` relative-distortion estimator for the query-key inner product. Bits per token are independent of head dimension and scale only logarithmically with context — a natural fit for an indexer key that only needs correct ordering.
- **Product Quantization (PQ)** as in PQCache (SIGMOD 2025): partition each key into sub-vectors, quantize each against a k-means codebook, and turn attention-score estimation into a table lookup / MIPS over centroids. PQCache treats KV as an embedding-retrieval problem, keeps compressed keys, and fetches on demand.
- **A²ATS** (Findings of ACL 2025, arXiv:2502.12665): query-aware vector quantization of key states plus Windowed RoPE so a shared codebook works. Per the paper, "A2ATS causes auxiliary memory usage (0.008) identical to eviction-based methods… while being significantly more memory efficient than… Quest (0.031) and MagicPIG (2.344)," with throughput "up to 2.7 times higher than traditional full attention methods." This is the closest general precedent for "vector-quantize the keys used for selection."

### 3. Learned hashing / LSH (compress key to bits, score with bit-ops)
- **HashAttention** (Desai et al., ICML 2025, arXiv:2412.14468): learns mappings that encode queries and keys into Hamming space so pivotal-token identification becomes bitwise operations. The paper "reduces tokens used by up to 16× with minimal quality loss, requiring only 32 bits of auxiliary memory per token. Sparsity can be further improved to 32× through task-specific fine-tuning. On A100 GPU, at 32× sparsity… reduces attention latency by up to 4.3× in GPT-FAST and 2.54× in FlashDecode." Framed explicitly as solving the MIPS problem while being GPU-friendly and handling the query/key distribution mismatch that off-the-shelf MIPS solvers stumble on.
- **MagicPIG** (ICLR 2025): LSH *sampling* (not top-k) with theoretical guarantees, offloading hash tables and reduced attention to CPU; up to 2.9× throughput. Shows pure top-k can degrade on aggregation tasks — relevant because an aggressively compressed indexer must still preserve the *set* it returns.
- Earlier **Sparse Attention with Learning to Hash** (Sun et al., ICLR 2021) and Reformer-style LSH attention are the conceptual ancestors.

### 4. Hierarchical / multi-stage selection (cut how many keys you fetch)
- **HISA** (Hierarchical Indexed Sparse Attention, 2026): a *drop-in, training-free* replacement for the DSA indexer. Stage 1 mean-pools indexer keys into blocks (block size B=128) and scores block representatives to keep top-m blocks; Stage 2 runs the original token-level indexer only within those blocks. Preserves the identical top-k token set consumed by Sparse MLA, drops per-query cost from O(L) to O(L/B + mB), and delivers up to 3.75× indexer-kernel speedup at 64K under a fixed 8K candidate budget (2.16× at 4:1 compression). This is the template for a remote-Indexer-K design: fetch only pooled block summaries first, then fetch full keys for a small candidate set.
- **Native Sparse Attention (NSA)** (DeepSeek, 2025): three branches — compressed (mean-pooled blocks), selected (top-n blocks), sliding window — natively trained. The compression branch is itself a coarse key representation used to drive selection.
- **RetroInfer's wave index** (VLDB 2026) and **RetrievalAttention** (NeurIPS 2025): build ANNS structures (spherical k-means / IVF-style centroids, graph indexes) over keys; centroids are compact GPU-resident proxies while full vectors sit in CPU/remote memory — cutting PCIe traffic to <2% of full attention. Both flag the query-key out-of-distribution problem that breaks naive ANNS.
- **Quest** (Tang et al., ICML 2024): stores per-page min/max key metadata as a compact proxy and estimates page criticality with the query — a cheap, lossy coarse filter that "can achieve up to 7.03× self-attention speedup, which… reduces inference latency by 2.23×… with negligible accuracy loss." **Twilight** uses 4-bit quantized keys for coarse scoring then adaptive top-p pruning.

### 5. Low-rank factorization of the key matrix
- **ShadowKV** (ICML 2025 Spotlight, arXiv:2410.21465): pre-RoPE keys are exceptionally low-rank; store a low-rank key cache on GPU and offload values to CPU, reconstructing sparse keys on the fly. It "boosts generation throughput by 3.04× for Llama-3.1-8B with… a batch of 122K contexts" and supports "up to 6× larger batch sizes… without sacrificing accuracy." Directly suggests SVD-compressing the indexer key or storing it as a low-rank factor.
- **InfiniGen** (OSDI 2024): uses offline SVD on the query/key weights to build a low-rank "rehearsal" that speculates the important tokens for the next layer and prefetches only those — a low-rank *predictor* rather than storage compression, but the same math.

### 6. Systems for disaggregated / remote KV with sparse attention
- **SAC (Sparse Attention on CXL)** (arXiv:2606.19746, 2026): the first disaggregated KV system built for sparse-attention models. It stores full KV in a CXL memory pool and fetches only top-k entries on demand at cache-line granularity, because RDMA is 4–19.7× slower than local DRAM for the small, scattered per-layer fetches sparse attention needs (CXL stays within 1.04–1.64×). "Evaluations on DeepSeek-V3.2 using SGLang show that SAC achieves 2.1× higher throughput, 9.7× lower TTFT, and 1.8× lower TBT compared to RDMA-based baselines," within 9% of the non-disaggregated upper bound. Crucially, SAC keeps indexer keys resident in HBM and offloads only the latent KV — leaving the exact gap the query identifies. It also quantifies that at 128K only 21% of KV is used and V3.2 needs 9.2 GB/request.
- **DeepSeek-V4 (official): FP4 indexer key cache** — the single most direct precedent for compressing Indexer K. V4 performs the lightning-indexer QK path in FP4 (with FP4 quantization-aware training). Per the vLLM DeepSeek-V4 blog (Apr 24, 2026): "we use fp4 for the indexer cache and fp8 for the attention cache, which further reduces the KV cache size by roughly 2× compared to the bf16 estimate," and "DeepSeek V4 only has 9.62 GiB KV cache per sequence at 1M context. That is about 8.7× smaller than the 83.9 GiB estimate for a 61-layer DeepSeek V3.2-style stack."
- **SparDA (Sparse Decoupled Attention)** (arXiv:2606.04511, 2026): adds a tiny "Forecast" projection (<0.5% params) that drives block selection one layer ahead so KV can be prefetched from CPU and overlapped; up to 1.25× prefill / 1.7× decode speedup, 5.3× decode throughput via larger batches. Compresses the *selection computation*, not the key storage.
- **IndexCache / IndexShare** (arXiv:2603.12201, 2026): adjacent DSA layers share 70–100% of selected tokens, so most indexers are redundant; retaining ~1/4 of indexers gives up to 1.82× prefill / 1.48× decode speedup with negligible quality loss (validated on a 30B DSA model at 200K context and preliminarily on GLM-5). This directly reduces how often you must fetch/score indexer keys.
- **InfiniGen** and **ScoutAttention** show the bandwidth reality: even with one-layer-ahead prefetching, GPUs can stall ~61% of the time on I/O — underscoring that any remote-Indexer-K design lives or dies on prefetch overlap and compression ratio.

### 7. Token-level compression / merging
Token eviction and merging (H2O, SnapKV, StreamingLLM, TOVA, LazyLLM, SlimInfer, PyramidInfer) reduce the number of keys to score at all. These are largely orthogonal but risky for an indexer, since permanently evicted tokens can never be recovered if the query later needs them — a reason DSA keeps the full context accessible.

## Details

**Why asymmetric quantization is the right frame.** The indexer only needs the correct *set* of top-2048 tokens; exact scores are irrelevant. That is the defining property MIPS quantization exploits. Keeping the incoming query in FP8/BF16 while storing the key in 1–4 bits (asymmetric distance computation) preserves ranking accuracy for the high-inner-product tail that determines top-k, which is exactly what ScaNN's anisotropic loss and QJL's sign-bit estimator are engineered for. The DSA indexer already applies a Hadamard transform to queries and keys before scoring — a rotation that spreads outliers and makes low-bit quantization far more forgiving, which is convenient because it means the model is already partway to a quantization-friendly representation.

**Two-stage fetch is the natural remote-memory architecture.** HISA and RetroInfer independently converge on the same shape: keep a tiny coarse proxy (pooled block key or cluster centroid) in fast/local memory, use it to shortlist candidates, then fetch full-precision keys only for the shortlist. For a remote Indexer K, the coarse proxies are cheap to keep in HBM (L/B of them), and only the candidate blocks incur remote-fetch bandwidth. Combined with cross-layer index reuse (IndexCache), the fetch amortizes across 3–4 layers.

**Storage compression precedents converge on 1–4 bits for keys.** Twilight finds 4-bit keys preserve the attention-weight mass needed for correct selection while 2-bit collapses it; DeepSeek-V4 ships FP4 indexer keys; QJL pushes to 1 bit with provable guarantees; HashAttention uses learned binary codes (32 bits/token). The consistent message: keys tolerate far more aggressive quantization than values when the goal is selection, not reconstruction.

**Bandwidth is the true constraint.** SAC's measurements show RDMA per-fetch latency of several microseconds and 4–19.7× DRAM latency for scattered small reads, while CXL reaches near-DRAM; InfiniGen shows 61% GPU stall even with prefetching. Any remote-Indexer-K scheme must (a) compress the key enough that the shortlist fits the bandwidth budget, and (b) hide latency behind computation via one-layer-ahead speculation (InfiniGen/SparDA) or cross-layer reuse (IndexCache).

## Recommendations

**Stage 1 — Compress the stored indexer key in place (low risk, immediate).** Apply asymmetric quantization: keep queries at FP8/BF16, store keys at 2–4 bits using per-block scalar quantization or product quantization with anisotropic (ScaNN-style) loss. Follow DeepSeek-V4's FP4 precedent as a proven floor. **Threshold to advance**: recall@2048 (fraction of the true top-k set recovered) ≥ 0.95 and downstream LongBench/Needle-in-a-Haystack within ~1 point of the FP8 indexer baseline.

**Stage 2 — Add a hierarchical coarse filter (HISA-style) to bound remote fetches.** Mean-pool indexer keys into blocks (B≈64–128), keep block proxies in HBM, and fetch full keys only for the top-m candidate blocks from remote memory. This is training-free and preserves the exact token-level top-k interface. **Threshold**: candidate budget mB should be tuned so that recall@2048 holds ≥ 0.95 while remote bytes/step fall below your interconnect's per-step budget; if recall drops, increase m before decreasing quantization bits.

**Stage 3 — Amortize with cross-layer index reuse and speculative prefetch.** Adopt IndexCache's F/S layer pattern (run the full indexer on ~1/4 of layers, reuse indices on the rest) to cut fetch frequency ~4×, and use one-layer-ahead forecasting (SparDA/InfiniGen) to overlap remote fetch with compute. **Threshold**: end-to-end decode throughput must beat the HBM-resident baseline; if GPU stall time exceeds ~20% (well below InfiniGen's 61% worst case), improve overlap or compression before adding more remote tiers.

**Stage 4 — If accuracy is the binding constraint, switch to learned hashing.** If quantization recall plateaus below target, adopt HashAttention-style learned binary codes (trained via distillation against the original indexer's selections, as IndexCache and SparDA do). This trades a small training cost for materially better recall-per-bit than data-oblivious quantization.

**Measurement discipline.** Never optimize score MSE; optimize *set recall* of the top-2048 and end-task quality. MagicPIG's finding that top-k can under-select on aggregation tasks means you should also monitor tasks that need broad attention, not just retrieval.

## Caveats
- **No end-to-end published solution exists** for the exact problem (remote Indexer K under bandwidth pressure). This report assembles the solution from adjacent components; integration risk is real.
- **Recency and verification**: several cited works are very recent or forward-dated 2026 preprints (SAC, HISA, SparDA, IndexCache, DeepSeek-V4, LiteTopK, StreamIndex). Some efficiency numbers are self-reported and not independently reproduced; treat FlashMemory-style claims (90% KV reduction, 2.8× throughput) as unverified.
- **Query-key OOD problem**: RetrievalAttention and A²ATS both document that queries and keys occupy separated distributions, so off-the-shelf ANNS/quantization can fail; the indexer's Hadamard transform and query-aware codebooks (A²ATS) mitigate but do not eliminate this.
- **DSA specifics vary by model**: indexer head counts, top-k, and precision differ across V3.2, GLM-5/5.2, and V4; the 64-head/132-byte figures are for DeepSeek-V3.2 in SGLang and should be re-derived per target model.
- **Storage vs. bandwidth**: DSA already does not reduce KV *storage*; compressing Indexer K reduces both HBM footprint and remote-fetch bandwidth, but the top-k=2048 latent KV fetch remains a fixed floor that compressing the indexer cannot remove.
